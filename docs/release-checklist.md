# Release checklist: Stage G section 5 (owner actions)

Stage G sections 1–4 are done (see [`stage-g-review/`](stage-g-review/README.md)). What remains
are owner decisions and the first release. Work through the steps in order; each one says how to
verify it.

The three publishable packages are `@time-fit/core`, `@time-fit/storage-prisma`, and
`@time-fit/integrations`. All three are currently `"private": true` at version `0.0.0`.

## 1. Secure the npm package names

- [ ] Sign in at npmjs.com and create the organization **`time-fit`** (Add Organization → free
      plan for public packages). This reserves the `@time-fit/*` scope.
- [ ] Turn on two-factor authentication for your npm account (needed to publish).
- [ ] **If `time-fit` is already taken:** use the fallback names from
      [ADR 0007](adr/0007-packaging-and-names.md) (`timefit-core`, `timefit-storage-prisma`,
      `timefit-integrations`). Record the change in a new ADR, then rename across:
      - package manifests and peer ranges;
      - imports in `examples/`, `apps/take-a-break`, and the READMEs;
      - `scripts/check-core-dependencies.mjs`, `scripts/check-published-dependency-licenses.mjs`,
        `scripts/verify-packed-quickstart.sh`, and `.changeset/config.json`.

      Re-run all CI checks after the rename.

Verify: the organization page `npmjs.com/org/time-fit` lists you as owner.

## 2. Merge the refactor into `main`

- [ ] Review and merge PR **#30** (`refactor-1` → `main`).
- [ ] After merging, confirm CI is green on `main`. All six jobs should pass, including Test on
      Node 20/22/24.
- [ ] Check that GitHub recomputed the Dependabot alerts for `main`. The stale
      `package-lock.json` (147 alerts) and the old `apps/fitbit-break` path (52 alerts) should
      disappear. Remaining legacy alerts are accepted per
      [`contrib/legacy/README.md`](../contrib/legacy/README.md).

From here on, Changesets compares against `main` (`.changeset/config.json` `baseBranch`).

## 3. Prepare the first version

- [ ] Choose the first version. `0.1.0` is suggested: pre-1.0 signals the API may still change.
- [ ] Run `yarn changeset`, select the three packages, choose **minor**, and describe the first
      release. Then run `yarn version-packages`. This bumps the versions and writes each
      package's `CHANGELOG.md`.
- [ ] In `packages/core/package.json`, `packages/storage-prisma/package.json`, and
      `packages/integrations/package.json`, change `"private": true` to `"private": false`
      (or remove the field). This is the owner release decision that sections 2–4 deliberately
      did not make.
- [ ] Peer ranges `@time-fit/core: ">=0.0.0 <1"` in storage-prisma and integrations still match
      `0.1.0`; optionally tighten them to `^0.1.0`.
- [ ] Add `"/CHANGELOG.md"` to each package's `files` list so the changelogs written by
      `yarn version-packages` ship in the tarball. npm does not include `CHANGELOG.md`
      automatically when `files` is set.
- [ ] Commit (for example, "Release 0.1.0") and confirm CI is green.

## 4. Publish dry run

For each package, from the repository root:

```sh
yarn workspace @time-fit/core npm publish --access public --dry-run
yarn workspace @time-fit/storage-prisma npm publish --access public --dry-run
yarn workspace @time-fit/integrations npm publish --access public --dry-run
```

- [ ] Each listing includes `src/`, `types/` (generated by `prepack`), `README.md`, `LICENSE`,
      and `package.json`, and nothing else (no tests, coverage, or generated clients).
- [ ] `./scripts/verify-packed-quickstart.sh` still passes.

Scoped packages need `--access public`; without it npm treats them as paid private packages.

## 5. Decide on provenance

npm provenance (a signed link from the package to the exact commit and build) can only be
generated when publishing **from GitHub Actions** (`--provenance`). Choose one:

- [ ] **Publish locally for 0.1.0** (simplest; no provenance), or
- [ ] **Add a publish workflow** that runs on a tag or release, with `id-token: write`
      permission and an npm automation token stored as a repository secret. Then publish with
      `yarn npm publish --access public --provenance`. Write the workflow as a reviewed change; none
      exists yet by design.

## 6. Publish

Publish `@time-fit/core` first, since the other two have it as a peer:

```sh
yarn workspace @time-fit/core npm publish --access public
yarn workspace @time-fit/storage-prisma npm publish --access public
yarn workspace @time-fit/integrations npm publish --access public
```

- [ ] Tag the release in git (for example `@time-fit/core@0.1.0`) and create a GitHub Release
      with the changelog entries.
- [ ] Verify from a clean directory, outside the repository:

  ```sh
  mkdir /tmp/timefit-check && cd /tmp/timefit-check && npm init -y && npm pkg set type=module
  npm install @time-fit/core
  # copy examples/quickstart/index.mjs here, then:
  node index.mjs
  ```

## 7. After publishing

- [ ] Remove the "not yet published to npm" note from `README.md` and `packages/core/README.md`.
- [ ] Update `CITATION.cff`: add `version` and `date-released` for the release. Optionally
      archive the release on Zenodo, which gives a DOI that can then go in the `doi` field.
- [ ] Add a progress-log entry recording the release, and mark Stage G (and the plan's
      definition of done) complete in `docs/jitai-library-plan.md`.
